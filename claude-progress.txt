Feature: Teller sync cursor advancing past pending transactions, causing
         settled transactions to be silently skipped on future syncs

Root cause: In sync_teller_account(), after fetching transactions from

  past them. When those transactions eventually settled and posted

  returned by Teller again — silently dropped forever.

  The account balance updates and budget threshold notifications still
  fired normally (balance is a separate API call; a pre-existing
  notification triggered the user's suspicion), masking the bug.

      After:  if posted: account.teller_cursor = posted[0].id
    Cursor now only advances to the newest *posted* transaction.
    Pending transactions above it are re-fetched on each subsequent sync
    until they settle; deduplication via external_id handles re-inserts
    safely once they post.

  - Diagnosed that the user's missing 5/22-5/25 transactions were simply
    still pending at Teller (weekend settlement lag), not a data loss

=== 2026-05-26 — Infrastructure session (Security architecture design) ===

What was worked on: Security and data privacy architecture review — no code
changes; design decisions and future feature planning.

Status: Complete (design/decisions only)

Commits made this session: none

What was done:
  Threat model defined for Hearth cloud tier:
    #1 Database breach — attacker gets a DB dump
    #2 Server compromise — attacker gets shell access to running server
    #3 Hearth itself can see user data — trust/policy concern
    #4 Legal compulsion — subpoena or NSL forces disclosure

  Key design decisions made:
  - Threats 1 & 2 addressed via field-level encryption (security-001, done)
    and DB-level encryption at rest on managed Postgres (security-000, deploy
    checklist).
  - Threats 3 & 4 require zero-knowledge / E2EE (security-002). Deferred —
    ZK is complex (password recovery, household key sharing, breaks server-side
    AI features) and only matters for the cloud tier. Will be offered as opt-in
    during onboarding with explicit trade-off disclosure.
  - Phase 3 encryption (notes, messages, transactions, contacts) deferred
    pending search architecture decision (security-003). The core tension:
    full-text search and field encryption are architecturally in conflict.
    Blind index approach (HMAC of normalized value) is viable for transactions
    and contacts but not full-text. Decision deferred to be co-designed with
    the global search feature (search-001).
  - Transaction data retention policy discussed: purge raw transactions older
    than 24 months (user-configurable), keep only monthly category aggregates.
    Requires a BudgetMonthlySummary materialized table first (budget-021).
    Not urgent — no live users yet, 24-month clock hasn't started.
  - Warrant canary noted as a low-cost cloud-tier option (security-004).
  - Legal compulsion realism: as a small company, fighting subpoenas is
    cost-prohibitive. Best defense is not holding the data (ZK + retention
    policy) rather than litigation.

  Context on ZK trade-offs (for future reference):
  - Password reset impossible with pure ZK; recovery codes are the substitute.
  - Server-side AI features (coach digest, journal signal extraction) cannot
    read ZK-encrypted fields. User must either accept a "decrypt → AI → re-encrypt"
    flow or opt out of those AI features.
  - Household shared data requires a household key encrypted per-member; new
    member joins require key exchange from an existing member.
  - Conclusion: ZK is right for power users / privacy-conscious segment, wrong
    as a default. Opt-in toggle with clear trade-off disclosure is the correct
    product decision.

What was left:
  All design decisions. Implementation of security-002 (ZK) is future cloud-tier
  work. security-003 (Phase 3 encryption) to be revisited alongside search-001.

Recommended next step:
  No immediate security work needed. Phase 1 + 2 encryption is shipped.
  Next security work is triggered by: (a) cloud deployment (enable DB encryption
  at rest, security-000), (b) designing global search (security-003 evaluation),
  or (c) building the cloud tier's privacy settings (security-002).

=== 2026-05-26 — Coding session (note-editor double-create fix) ===

Status: complete

What was worked on:
  Brandon reported clicking the "+" button on a journal collection
  was creating TWO notes (one selected, one orphaned in the list).
  Root cause: the auto-create-on-mount useEffect in
  web/src/components/notes/note-editor.tsx fired createNote() POST
  TWICE under React 18 Strict Mode's dev-only effect double-
  invocation. The existing `cancelled` flag only suppressed the
  React handler — by the time it flipped to true, the network
  request was already in flight. Cleanup ran, then the effect re-
  fired with a fresh closure (refs survive Strict Mode but local

  for the first POST then saw `cancelled=true` and didn't call
  onCreated, so the parent only learned about the second note while
  the first was an orphan in the database.

  This is a *dev-only* symptom (production builds disable the double-
  invocation) but it violates the project's "Write idempotently"
  principle in CLAUDE.md regardless. The bug affects every collection
  with a + button, not just journal — journal made it visible because
  the date-sorted list made the duplicate obvious.

  web/src/components/notes/note-editor.tsx:
    - Added `const hasCreatedNewNoteRef = useRef(false);` next to
      the existing hasInitializedRef.
    - The auto-create useEffect now short-circuits if
      hasCreatedNewNoteRef.current is true, and flips it true BEFORE
      calling createNote() (so even if the cleanup races, the second
      run sees the guard).
    - Kept the existing `cancelled` flag as a second line of
      defence — it still protects against the legitimate case where
      the component truly unmounts mid-create (user navigates away).
    - Comments explain WHY the ref guard exists so future me doesn't

=== 2026-05-26 — Coding session (note-editor spinner regression fix) ===

Status: complete

What was worked on:
  My previous ref-guard fix introduced a regression: clicking + now
  spun forever and never completed even though the note WAS created
  in the database. Root cause was a stale interaction with the
  legacy `cancelled` flag.

  Strict Mode lifecycle with both the ref guard AND the cancelled
  flag in place:
    1. Effect run A: ref=false → flip to true, setSaving(true), fire
       createNote(). Locally captures `cancelled_A = false`.
    2. Cleanup A: flips cancelled_A = true.
    3. Effect run B: ref=true → bail early. No new POST. (Good.)
    4. POST from A resolves. .then() in A's closure checks
       cancelled_A, which is TRUE because of step 2. Bails.
    5. onCreated never fires. Parent never learns about the note.
       setSaving(false) never runs (also gated on !cancelled_A).
       Editor stays in isNew=true forever, spinner spins forever.
       Note IS in the DB; the frontend is just blind to it.

  The `cancelled` flag's original purpose was to suppress
  setState-after-unmount when the user navigates away mid-create.
  But Strict Mode's pseudo-unmount between the two effect runs
  triggers the same cleanup that a real unmount does, and the flag
  can't tell them apart. Combined with the ref guard, the cancelled
  flag is a net negative.

What was done:
  web/src/components/notes/note-editor.tsx:
    - Removed the `cancelled` local var and its cleanup return.
    - .then() / .catch() / .finally() now run unconditionally for
      the single POST that the ref guard allowed through.
    - Updated the comment block to record WHY the cancelled flag
      was removed and what trade-off was made (setState-after-
      unmount on real navigation is a harmless dev warning in
      React 18, not a crash).

  The flow now:
    - Click + → editor mounts isNew=true with fresh ref.
    - Strict Mode run A fires createNote, flips ref to true.
    - Cleanup A: no-op.
    - Strict Mode run B: ref is true, bail.
    - POST resolves → .then runs → invalidates queries → onCreated
      fires → parent setSelectedId(real_id) → React unmounts the
      isNew=true editor (key changed) and mounts a fresh one in
      edit mode with the real note loaded.
    - The old isNew editor's .finally() setSaving(false) runs after
      unmount — harmless React 18 no-op.

What was built (backend — new events/ package):

WORKED ON: Railway pre-deploy failure — `alembic upgrade head` crashed in
migration 0046 (journal kind backfill).

STATUS: complete (fix verified locally; not yet committed or pushed).

COMMITS: none — working tree change only, left for Brandon to commit/push
(main pushes stay human per CLAUDE.md).

WHAT WAS DONE:
  Root cause. 0046 declared its Core table with
  `sa.column("domain", sa.String())`. SQLAlchemy's **asyncpg** dialect renders
  explicit casts on bind params, so the predicate compiled to
  `collections.domain = $1::VARCHAR` against a column whose production type is
  the native enum `collection_domain` (created in 0013) — and Postgres has no
  `enum = varchar` operator. Confirmed identical rendering on SQLAlchemy
  2.0.36 / 2.0.43 / 2.0.51, so it is not a version-resolution fluke.

  Fix. Declared the column as
  `sa.Enum("notes", "documents", name="collection_domain")` instead of casting
  at the one call site. Compiled output:
    - asyncpg SELECT: `domain = $1::collection_domain`   (was `$1::VARCHAR`)
    - asyncpg INSERT: `domain` binds `$3::collection_domain` (was `$3::VARCHAR`)
    - SQLite (both): plain `?` — unchanged.
  No DDL is emitted from a Core `sa.table()`, so the enum type is never
  created or dropped by this migration.

  Note the INSERT in step 2 had the SAME defect. Casting only the WHERE clause
  (the obvious one-line fix) would have cleared the SELECT and then failed the
  deploy again on `column domain is of type collection_domain but expression
  is of type character varying` for any household needing a seeded journal.
  Typing the column fixes both sites at once.

VERIFICATION:

     after, and diffed the rendered casts. ✓
  2. Executed `upgrade()` end-to-end against a real SQLite DB seeded with

WHAT WAS DONE:

  create_all-built DB therefore had a different COLUMN TYPE than a

  included.

  added via batch_alter_table so a DB created before this revision matches one
  created after. Without that, the same drift reappears in miniature.

What was done
-------------
A third permission tier ordered read < propose < write. An agent write that
previously either executed or 403'd now has a middle outcome: it is captured as
a pending Proposal for a human to approve or reject.

New package api/src/life_dashboard/proposals/ — models.py (one table), service.py
(record / approve / reject / expiry sweep), executors.py (tool name -> the
function that performs its write), schemas.py. Migration 0051, one table, single
head confirmed.

Design decisions that firmed up during the build, all recorded in
plans/open-hearth/agent-proposals.md:

* The propose ceiling is an OPT-IN "propose" key inside a domain's action config
  ({"todos": {"create": "member", "propose": "viewer"}}) with no default.
  merge_with_defaults never invents it, so the backward-compatibility guarantee
  is mechanical rather than a promise — no existing household can resolve to
  propose unless an admin explicitly sets it.
* Idempotency is a SHA-256 fingerprint over (tool, args, proposer, token) under
  a PARTIAL unique index (WHERE status='pending'). A hash rather than a JSON
  comparison because JSON equality is not portable across Postgres and SQLite,
  and because folding the two nullable proposer columns into the digest makes
  them dedupe — SQL NULLs never compare equal, so a NULL-bearing unique index
  would let every household-agent proposal through. Partial so that re-asking
  AFTER a decision is a new request, not a duplicate.
* Deciding is an atomic UPDATE ... WHERE status='pending' RETURNING id claim,
  not SELECT ... FOR UPDATE. The executor's own service call commits, which
  would release the lock mid-approval; the claim is what actually stops two
  admins executing one write twice.
* Each MCP write tool split into a thin tool plus a registered _perform_*
  function. "Approval executes through the same service function as the direct
  path" is now structural rather than a convention — there is exactly one copy
  of the write, and the approval path calls it.
* proposals.token_id is CASCADE, NOT ON DELETE SET NULL (the opposite of
  audit_log.token_id). Under SET NULL a revoked token and a household-agent's
  legitimately absent token are indistinguishable and the stale-proposer guard
  fails open. Verified in both real databases, not just asserted.
